# 需求与业务规则

这份参考文档用于把“看起来像某个产品”变成可执行的产品约束。它来自薪跳项目中反复出现的需求：工作日、上下班、午休、通勤和实时金额必须由同一套规则驱动。

## 先问清楚的变量

- 目标平台：网页预览、macOS 菜单栏应用，还是两者都要。
- 主界面和快捷入口的关系：快捷入口只显示什么，点击后打开什么。
- 哪些设置用户可以修改，哪些值属于固定产品规则。
- 工作日是否允许逐日选择；未选中的当天应该显示什么状态。
- 午休是纯展示还是从有效工作时长中扣除。
- 通勤是否计入工作时长；如果计入，分别填写上班前和下班后的分钟数。
- 金额是固定目标、按分钟增长，还是来自外部数据；实时数据是否需要持久化。

## 推荐的数据模型

使用一个可校验的 canonical schedule，而不是在多个组件里各算一遍：

```text
workdays: [1..7]                 # Monday-Sunday
workStart: "09:00"
workEnd: "17:30"
lunchEnabled: boolean
lunchStart: "12:00"
lunchEnd: "13:30"
commuteEnabled: boolean
commuteBeforeMinutes: number
commuteAfterMinutes: number
hourlyRate: number
```

派生结果至少包括：effective start/end、paid minutes、当前进度、当前金额、剩余时间和当天状态。通勤打开时扩展有效区间并计入 paid minutes；午休打开时只扣除午休区间。未选中的工作日应返回休息状态、零进度和零当前收入。

## 状态和持久化

- 表单编辑使用 draft；通过校验和保存后，才替换 committed settings。
- 时间格式、分钟数、开始结束顺序、午休是否落在工作区间内都要校验。
- 浏览器预览可以安全地使用 localStorage；原生壳需要明确数据落盘位置和失败处理。
- 菜单栏数字、主看板数字和测试断言必须消费同一份派生结果，不能各自复制算法。

## 验收标准样例

- 切换工作日后，当前日期的休息/工作状态立即正确。
- 打开或关闭午休，paid minutes、进度、倒计时和金额同步变化。
- 打开通勤并填写分钟数，通勤时间同时影响有效区间和收入计算。
- 保存后重新打开设置，值保持一致；非法输入不会污染已提交配置。
- 点击 macOS 菜单栏金额后打开或聚焦完整看板；快捷入口不承担完整编辑能力。
