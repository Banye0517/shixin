# 验收、打包与 GitHub 交付

## 验收顺序

1. 先运行单元测试，覆盖核心业务规则和边界输入。
2. 运行生产构建与项目专用打包测试；确认输出目录包含预期入口文件。
3. 启动稳定的本地预览，在真实浏览器中验证主要点击路径、表单保存、窄视口和控制台错误。
4. macOS 应用单独编译、启动、打包并在系统 UI 中检查菜单栏行为。
5. 记录通过项、未验证项、阻塞原因和复现步骤；不把替代证据写成完整验收。

## 调试规则

- 遇到录屏中的异常，先复现、缩小范围、识别根因，再改最小范围代码。
- 构建通过只能证明编译链路，不证明视觉、点击、原生权限或发布权限。
- 浏览器截图、DOM 检查和系统 UI 观察是不同证据，不能相互替代。
- 浏览器 screenshot/CDP 不可用时，保留最强可用证据并标记像素级比较未完成。
- 任何失败命令都要修复或明确归因；不要在发布前留下含糊的“应该可以”。

## GitHub 发布边界

Skill 仓库只应包含 `SKILL.md`、`agents/openai.yaml`、必要的 `references/`、README 和真实可复用脚本/资源。不要提交 PayDance 源码、node_modules、录屏、参考图、构建产物、`.env`、Token 或本地绝对路径。

发布前：

- 只检查并 stage 已确认属于 Skill 的文件，禁止把混合工作区整体加入。
- 提交、推送和创建远程仓库是不同动作；用户必须分别明确授权。用户说“发布到自己的 GitHub”可视为授权这三个动作，但仍需要有效 GitHub 登录态。
- 先确认目标 owner/repository/branch 是否准确；本次目标默认是 `Banye0517/shixin`。
- `gh auth status` 显示 token 无效或网络不可用时，停止远程写入，不索要 Token；让用户在自己的终端执行 `gh auth login -h github.com` 后再继续。
- 发布结果要报告仓库 URL、commit、实际检查项和未完成的系统级验证。
